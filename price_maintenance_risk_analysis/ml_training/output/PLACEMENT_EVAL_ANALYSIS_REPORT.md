# placement_evaluation表和company_annual_scores表数据结构分析报告

## 🎯 核心问题分析

**Q: 那200-300个其他字段是不是直接从data目录脚本写入的或从原始数据copy的？**

**A: ❌ 不是！实际情况更加复杂和严重。**

## 📊 数据表结构分析

### 1. placement_evaluation表
- **字段数量**: 167个字段（除去系统字段）
- **样本数量**: 6,645个样本，3,045只不同股票
- **数据特点**: 
  - ✅ **定增相关字段覆盖率很高**（81%+）
  - ✅ **7个月收益率字段覆盖率81.16%**
  - ⚠️ **财务评分字段覆盖率仅33.21%**
  - ❌ **没有PB/PE/PS字段**

### 2. company_annual_scores表
- **字段数量**: 17个字段
- **记录数量**: 73,759条记录，5,396只不同股票，21年数据
- **数据特点**: 
  - ✅ **完整的年度财务评分数据**
  - ✅ **21年的历史数据覆盖**
  - ✅ **包含5大维度评分**

### 3. ml_features_wide表
- **字段数量**: 584个字段
- **样本数量**: 568,624个样本（placement + fake_quote）
- **数据特点**: 
  - ❌ **个股PB/PE/PS/市值覆盖率0%**
  - ❌ **同行PB/PE覆盖率0%**
  - ✅ **行业PB/PE覆盖率90%+**
  - ⚠️ **大部分字段覆盖率低于1%**

## 🔍 关键发现

### 发现1: 数据流断裂问题

**问题描述**: 
```
stock_daily_basic表（1687万条记录，PB/PE覆盖率99%/87%）
    ↓ ❌ 断裂
ml_features_wide表（PB/PE覆盖率0%）
```

**影响**: 
- 大量有价值的PB/PE数据没有进入ml_features_wide表
- 导致训练数据缺失重要估值特征

### 发现2: placement_evaluation表的角色定位

**实际角色**: 
- **不是完整的特征存储表**，而是**定增业务专用表**
- **主要存储**: 定增参数、财务评分、7个月收益率等业务特定数据
- **不包含**: PB/PE/PS/市值等基础市场数据

### 发现3: ml_features_wide表的字段来源真相

**584个字段的真实来源**:

1. **placement_evaluation表同步字段** (~40个字段，33%覆盖)
   - 财务评分字段: `总分_斜率`, `盈利能力_斜率` 等
   - 定增参数字段: `定增_发行价`, `定增_募资总额` 等
   - 收益标签字段: `return_7m`, `return_1m`, `return_3m` 等

2. **company_annual_scores表时间序列** (~100个字段，部分覆盖)
   - 总分时间序列: `总分_T`, `总分_T-1`, `总分_T-2`, `总分_T-4`
   - 各维度时间序列: `盈利能力_T`, `成长能力_T`, `偿债能力_T` 等

3. **各种因子计算结果** (~200个字段，低覆盖率)
   - Beta因子: `beta_mkt_60`, `beta_ind_120` 等
   - Alpha158因子: 技术指标、量价因子等
   - 其他因子: SUE、FCF、chip等

4. **行业和市场数据** (~50个字段，高覆盖率)
   - 行业估值: `行业PB`, `行业PE` 等（90%+覆盖）
   - 市场指数: `market_return_1m`, `大盘MA10_slope` 等
   - 行业分类: `一级行业`, `二级行业`, `三级行业` 等

5. **空的字段结构** (~200个字段，0%或低覆盖率)
   - 个股估值: `个股PB`, `个股PE`, `个股PS`, `个股市值` (0%覆盖)
   - 同行估值: `同行PB_均值`, `同行PE_均值` (0%覆盖)
   - 其他衍生特征: 大量字段覆盖率<1%

## 💡 数据架构真相

### 真实的数据流架构

```
【数据源层】
stock_daily_basic表 (1687万条记录，99%/87% PB/PE覆盖)
company_annual_scores表 (73,759条记录，21年财务评分)
placement_evaluation表 (6,645条记录，定增业务数据)
其他数据源 (行业数据、市场数据、因子数据等)

    ↓ ❌ 断裂的数据流

【目标数据层】
ml_features_wide表 (584个字段，568,624个样本)
├── 已填充字段 (~380个字段)
│   ├── placement_evaluation同步字段 (~40个，33%覆盖)
│   ├── company_annual_scores时间序列 (~100个，部分覆盖)
│   ├── 因子计算结果 (~200个，低覆盖率)
│   └── 行业市场数据 (~50个，高覆盖率)
└── 空字段 (~200个字段)
    ├── 个股PB/PE/PS/市值 (0%覆盖)
    ├── 同行估值字段 (0%覆盖)
    └── 其他衍生特征 (大部分<1%覆盖)
```

### 为什么有584个字段？

**推测的构建过程**:
1. **设计阶段**: 基于理想的特征工程需求，设计了584个字段的完整schema
2. **数据摄入**: 通过各种方式将现有的数据导入（placement_evaluation、company_annual_scores等）
3. **字段预留**: 为未来可能需要的特征预留了字段结构
4. **数据缺失**: 大量字段由于数据源缺失或数据流断裂而没有填充

## 🎯 结论和建议

### 核心结论

1. **ml_features_wide表不是"完整的特征存储"**
   - 更像是"特征工程的框架结构"
   - 只有少部分字段有实际数据
   - 大量字段是空的或覆盖率很低

2. **data目录脚本的真正作用**
   - **不是直接写入ml_features_wide表**
   - 而是向**placement_evaluation表**和**company_annual_scores表**写入数据
   - 然后通过某种同步机制将部分字段同步到ml_features_wide表

3. **那200-300个其他字段的真实来源**
   - **不是从data目录脚本直接写入的**
   - 而是**设计时预留的字段结构**
   - 大部分字段目前是空的或覆盖率很低

### 建议的解决方案

#### 短期方案
1. **修复PB/PE数据流断裂**
   ```bash
   # 从stock_daily_basic表回填PB/PE数据到ml_features_wide表
   python solve_pb_pe_backfill.py
   ```

2. **完善现有数据覆盖**
   - 检查所有低覆盖率字段的数据源
   - 建立完整的数据摄入流程

#### 中期方案
1. **重新设计数据架构**
   - 明确ml_features_wide表的定位
   - 确定哪些字段是必需的，哪些是可选的
   - 建立清晰的数据流架构

2. **标准化数据摄入流程**
   - 统一所有数据的摄入路径
   - 确保数据流的完整性和一致性
   - 建立数据质量监控

#### 长期方案
1. **重构特征工程系统**
   - 基于"三层一入口"原则重构
   - 建立统一的数据管理器
   - 实现标准化的特征工程流程

2. **建立数据治理机制**
   - 数据源管理
   - 数据质量监控
   - 数据血缘追踪
